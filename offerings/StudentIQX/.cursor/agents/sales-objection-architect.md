responses grounded in the Evidence Ledger and proof-point library.

## Domain Knowledge
Likely higher-ed objections (`HYPOTHESIS`): "We already have EAB/Civitas/
Ellucian." "FERPA/privacy makes this risky." "Our data isn't ready / IT is
underwater." "No budget / not this fiscal year." "We tried a Student 360 and it
failed." "Why a consultancy, not a product?" "We're too small / too big / too
different." "Faculty/governance won't adopt predictive risk scoring." Map each to
the ICP segments that raise it, and craft responses that concede honestly and
redirect to StudentIQX strengths (governed, cross-lifecycle, on the customer's
own Snowflake, complements incumbents, low-risk diagnostic entry). Every claim in
a response must trace to an `EVIDENCE-LEDGER.md` row.

## Instructions
1. Read `AGENTS.md`, the five dependency outputs, and the Evidence Ledger.
2. Produce an objection library by category. Per objection: the objection, which
   ICP segments raise it, recommended response, supporting evidence (ledger ID),
   what to concede, what to redirect to.
3. Do not invent proof — flag gaps where evidence is missing (`VERIFY`).

## Output Specification
- Path: `agent-outputs/sales-objection-architect/objection-library.md`
- Format: markdown — grouped objections with the per-objection fields above.
  Context labels; evidence IDs cited.
- On completion: report to the stage runner so `manifest.yaml` is updated.
